## 1. 主智能体怎样真正决定模型和分工

Hermes 的 [model_map](https://github.com/NousResearch/hermes-official-plugins/blob/8b5b6296bbb900f90e296b4729d2c9a5d1139825/advanced-delegation/model_map.py#L175) 将已配置路线变成模型能选的枚举。模型选路线名，宿主解析到提供方、模型和思考强度；密钥、地址等配置不成为模型可自由填写的参数。`profile_routes` 用同样方式限制可选身份。它并不是让主智能体任意创建账号或猜一个模型名称。

本项目之前存在两种不完整路径：

- 桌面主持人生成自然语言分工后，程序仍遍历全部成员；工作成员的调用函数还丢弃了传入的具体任务。
- 手机协作独立遍历成员，忽略主持人配置；修桌面并不会自动修好 APK。

本轮已改成共享的受限选择机制：`agent_model_selection.py` 读取配置/缓存，按后端分别列模型和真实支持的档位；`agent_group.dispatch_prompt/parse_dispatch` 将主智能体决策解析为选中成员、模型、强度和具体任务。未知模型、不支持的档位、重复或未知成员会在工作成员调用前被拒绝。简单问题可直接回答，无须把所有成员叫一遍。

桌面、QQ 群接入和手机协作复用该机制；通用任务调度的子任务也保存模型/强度，并在真实调用时写进该后端自己的参数位置。只改变本次调用副本，不修改好友的默认设置。MCP 的 `inspect_runtime(section="model_choices")` 支持按需分页查询当前好友的候选模型，不返回密钥或其他好友配置。

仍需区分：目录列出代表配置或缓存里有这个选择，不代表已经登录、有额度或支持当前全部工具权限。外部工具型后端如果不支持纯文本隔离，不能伪装成已具备该能力。

## 2. 长期执行：借鉴租约和收据，而非反复重发整个任务

OpenMuse 的 [TaskWorker](https://github.com/CopilotKit/openmuse/blob/a4944f4c471d3dc93b8bfc060b5da309b5216ab2/apps/server/src/engine/worker.ts#L123) 通过条件更新领取任务，维护租约与心跳；每次写检查点之前重新校验任务仍由自己持有。界面是服务的客户端，任务由后台工作者持有。

其 [工具结果缓存](https://github.com/CopilotKit/openmuse/blob/a4944f4c471d3dc93b8bfc060b5da309b5216ab2/apps/server/src/engine/model.ts#L86) 按工具与参数摘要复用已完成结果。这值得参考，但“外部操作完成、检查点尚未写入时进程崩溃”的窗口仍须单独处理，不能据此声称外部操作恰好执行一次。

本项目已有 TaskManager、执行租约、验收器和检查点，应继续补齐这些现有组件，不引入第二套任务框架。本轮手机协作新增调用前的持久标记、逐个成员结果与恢复检查；返回未确认时等待核查，不再次生成整份提示词。QQ 机器人发送也区分待发送、已发和未确认，收不到明确回执时不盲目重发。

## 3. 记忆与反思：模型提建议，程序决定能否成为经验

nanoMuse 的 [记忆整理器](https://github.com/nano-muse/nanoMuse/blob/154f076fdaed76f1ef5646895a1954dd74d237f9/nanomuse/memory/consolidate.py#L200) 先解析模型提出的修改，再验证引用的记忆 ID、重复修改、合并内容和单轮删除上限；用户手写记录不能被模型随意删除，修改保留历史。适合借鉴的是“提议与写入分离”，不是简单追加更多提示词。

也不能把所有带 Memory 名称的项目当成反思系统。Hermes 插件的 [Memory Wiki 核心](https://github.com/NousResearch/hermes-official-plugins/blob/8b5b6296bbb900f90e296b4729d2c9a5d1139825/memory-wiki/dashboard/memory_wiki_core.py#L1) 明确是确定性的只读历史聚合，不调用模型、不写记忆。

本项目本轮发现并修复了一个实际错误：`record_failure_experience` 原来把失败后的建议无条件标成 `tool_verified`、置信度 1，并写“验证解决方案”。现在默认是待验证的失败警示，真实验证后才能显式记录为已验证修复。未验证的系统共享猜测也不能通过其他好友的记忆查询传播。相似任务通过既有统一检索读取带来源的警示，不能把反思内容提升为新权限或系统规则。

**尚未完成：**模型自动反思、后台整理与实际验证结果之间的完整自动闭环，以及用户纠正的持续学习质量。此次修复的是错误的验证标记和可见范围，不能称为已完成全套反思功能。

## 4. 后台整理可以选普通模型，不限定离线

用户进一步澄清：整理不限定离线，智能体工具内部的模型也与普通模型一样，只需要能独立选择，不另做一套“小模型框架”。本轮已将 `main.refresh_memory_if_due → memory_management.refresh` 接到 `background_generation.generate`。

本轮实现边界：

1. `background_model` 可独立指定普通后端、模型与思考强度；不设置则保留原来的聊天配置路径，不强制本地或云端。
2. 包括原有 CLI/API、DSH、反重力与外部智能体工具；实际调用仍过同一个后端、登录及权限边界。不能枚举的工具沿用它已配置的模型，不制造“通用思考档位”。
3. 修改只作用于本次后台调用副本，不改聊天默认模型，不因选择而重复下载权重或创建账号。
4. 模型继续输出结构化记忆提议；来源快照、写入版本、锁定条目和好友隔离仍由原程序执行。原生工具型后端沿用普通调用的工具权限，不能把它宣称为完全禁用工具的隔离推理。

真实验证使用隔离数据：聊天模型配置为 Sol／高，后台明确选 Luna／低；只调用一次，将两条合成偏好写入并从实际 SQLite 读回，13.758 秒完成。没有额外 QQ 消息。这证明当前 Codex 路线及记忆提交链，不证明每个 CLI/API 或离线模型均已验收。

另新增每好友 `model_api.quota_reply`：额度不足时发送用户填写的纯文本，不请求模型改写；空白表示不额外回复。按好友持久化一次发送状态，未确认发送不重试，正常模型回复恢复后才开始下一次额度提示周期。临时限流、认证失败和网络超时不当作“额度用完”。

## 5. APK：同步一套执行事实，明确手机是否真的能执行

nanoMuse 的 [设备架构](https://github.com/nano-muse/nanoMuse/blob/154f076fdaed76f1ef5646895a1954dd74d237f9/docs/every-device.md) 为目标设备建立独立执行会话，并传递进度、结果与审批；对话同步和任务委派是不同协议。它的 Android [ToolLoopDetector](https://github.com/nano-muse/nanoMuse/blob/154f076fdaed76f1ef5646895a1954dd74d237f9/android/src/android/app/src/main/java/com/openminis/app/agent/ToolLoopDetector.kt#L62) 还区分重复参数、结果无变化的轮询和未知工具循环。

本项目 APK 目前是桌面服务的客户端。优先修好真实的主持人、权限、分工、模型、强度、检查点与状态展示；不能因为增加一张手机卡片，就宣称手机已有独立离线智能体。

本轮手机代码已接入共享主智能体调度，允许在协作页选择主持人、查看本轮模型/强度/任务与返回状态；切换房间清理旧结果。另修复一个无关接口 403 会令整个手机应用显示离线的问题：各区域独立处理权限不足，不扩大设备授权。

**尚未验证：**实体手机安装与实际交互、后台保活、跨网/断网恢复、语音以及不同 Android 系统组合。本轮构建是预览 APK，不是正式签名发行，也不是独立本地执行引擎。

## 6. 研究验收不能只借鉴名称

nanoMuse 的 [goals/evaluation.py](https://github.com/nano-muse/nanoMuse/blob/154f076fdaed76f1ef5646895a1954dd74d237f9/nanomuse/goals/evaluation.py#L1) 明确注明：该库默认不改变目标状态，也不在主循环里自动运行，调用者仍须提供可信收集与决策链。这里有可参考的数据契约，不能据此当作已经完成的长期研究闭环。

本项目研究部分继续使用现有研究契约、实验收据和范围约束；有限数值实验不能升级成普遍证明。自动消融、独立保留集和多日无人值守仍需单独实现和验收。
