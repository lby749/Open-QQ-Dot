# MCP 全面审查与降耗方案

日期：2026-11-10。对象：桌面“openqqdots-最终发布”的最新版源码压缩包。

## 结论

值得使用 MCP，但收益主要来自**按需读取、共享执行结果、少传重复上下文**，不是把所有提示词换成 MCP。当前项目已经部分使用 MCP 和原生工具调用；重新造一套平行工具系统会增加维护和调用成本。

首要顺序：修复协作上下文重复 → 工具结果分页与引用 → 增加脱敏的运行能力查询 → 大工具目录按需发现 → 补齐不同智能体的适配。缓存和会话续接已有实现，应扩展复用而非推倒重写。

用户最新约束：**不使用 Claude**。本轮没有调用任何真实模型，没有向 QQ 发送消息；后续不得调用 Claude 或运行其相关测试，除非用户改变要求。Claude 相关结论仅来自源码阅读。

### 3.2 协作上下文重复

构造 40 条短合成消息，消息既进入 room.messages，也进入 room.memory，按现有 shared_memory/prompt_for 组装：

- 单成员输入 **8,621 字符 / 23,109 UTF-8 字节**。
- **40/40 个消息标记均出现至少两次**。
- 仅作诊断，移除共享记忆块后：**4,295 字符 / 11,663 字节**，字符数减少约 **50.2%**。
- 这不是可直接上线的“删掉长期记忆”方案：真实长期事实应保留，需区分持久事实、最近消息和已完成产物，按稳定 ID 去重。

| 成员数 | 构造请求数 | 合计输入字符数 |
|---|---:|---:|
| 1 | 2 | 12,483 |
| 3 | 4 | 29,745 |
| 6 | 7 | 55,638 |
| 12 | 13 | 107,428 |

这是冻结历史的静态比较，没有模拟新回复增长，没有执行模型，也不包含供应商附加指令和输出。证明重复被多个成员放大，不能用此表断言真实节省相同比例。

### 3.3 本地 MCP 实际进程验证

仅启动项目自己的 `topic_library.py` 子进程，临时好友、工作任务、无电脑工具：初始化、列工具、拒绝未授权工具、ping 均返回，进程退出码 0。

## 5. 深层问题与改动边界

### P0：群协作先保证身份、任务和上下文准确

1. `agent_group.py:131,152,165` 同一消息写入消息与长期记忆并双重投递；应将“持久事实”和“最近对话”分开，稳定 ID 去重，给每个角色只提供其分工和相关产物。
2. `house_qt/agent_group.py:330` 捕获 owner 后，后台仍读取 `self.house.friend_dir/profile_path` 和可变化的 `self.room_id`；静态存在切换好友/房间的竞态风险。启动前冻结所有运行标识，回写核对原范围，禁止跨好友复用会话或查询结果。**尚未做真实界面竞态复现。**
3. `house_qt/agent_group.py:350` 只把成员模型写到通用 model；Claude/Antigravity 等读取专用模型字段，可能没有实际选中指定模型。应由供应商适配器统一映射，避免模型切换无效引发反复重试。**此结论为源码路径推断，未真实调用。**
4. 优先复用 `prompt_context.task_session_prompt` 已有 owner/task/project/provider/role 绑定与配置指纹；不要直接把所有 ephemeral=True 改成 False。不同供应商的会话隔离、权限、压缩和恢复需要分别验收。

### P1：MCP 接入和权限不能靠提示词兜底

- 现有 stdio 实现应正确处理无效 JSON、请求验证和版本协商；当前初始化直接回显请求版本，不代表兼容该版本所有能力。
- `agent_tool_adapters.mcp_list_tools` 只读取一次 tools/list，未跟随 nextCursor。遇到分页服务器可能漏工具；应有总量/超时限制再收集，而非无限加载。
- 本地 `topic_library` tools/list 返回整份清单，没有服务端分页；首先保证排序稳定，再按实际规模决定是否添加分页。
- Claude/Codex 合并外部 MCP 配置时未见内建服务名的保留名保护；配置不应意外覆盖好友工具、手机或协作邮箱服务。配置属于用户授权输入，但名称冲突仍会造成能力错接。
- MCP 查询必须从服务器绑定身份取得 owner/account/project/task，不能信任模型传入的“我要查询某好友”。缓存键至少区分身份、权限、配置/数据版本；拒绝记录不可作为其他好友的可用结果复用。
- 工具清单、可用模型列表应注明“静态配置/缓存检测/实际调用验收”的证据等级；不能把目录中的模型文件名当作一定可运行的模型。
- 配置查询只返回明确白名单字段，隐藏密钥、访问令牌、授权头、凭据路径、命令环境变量及带密钥 URL。修改配置/发送消息/执行任务仍须走现有权限与审批，模型不能自己授予权限。

### P1：上下文与缓存已有基础，也有缺口

- `prompt_cache_layout.py` 已分离程序规则、稳定好友信息、动态上下文，并避免把用户人设提升成系统权限。
- `api_backend.py:409` 已有缓存模式、按目录隔离的缓存提示键和稳定工具排序；`prompt_context.py:362` 已有任务续接防重复逻辑。保留这些机制。
- `provider_context.py` 注释称保守窗口，但多数供应商默认上限写为 1,000,000；仅少量模型细分。上限应由可信模型元数据及用户下调配置决定，未知模型保守处理。**不是声称某个当前模型一定不支持 1M，而是静态供应商值无法证明所有模型支持。**
- `api_backend` 已分别记录供应商返回的输入、输出、缓存读写；继续把估算值和真实值分开。CLI 仅有字符长度时不能展示“真实 Token 节省”。
- 相同工具集保持稳定顺序和描述；不要每条消息随机改名/改描述。配置更新应版本化、使旧会话能力失效，而不是继续用旧权限。

## 6. 不建议做的事

- 不将人格、基本回复方式、必要安全与任务范围全部移到远端资源里：模型首次回答仍需要这些最小指令。
- 不强制普通 QQ 闲聊每轮查全部配置、模型状态和历史；额外工具往返可能更贵、更慢。
- 不把每个 Python 模块单独启动成 MCP 服务；复用现有共享工具服务与执行边界。
- 不为消耗问题盲目压低 Top-K、删工具或缩短所有上下文；这可能让任务缺少必要证据、增加失败重试。
- 不直接采用能任意执行代码的“万能 MCP”绕开 ToolRegistry；批处理优先复用已批准的工作流/胶囊，产物保留引用及审计记录。
- 不把 MCP 协议分页、客户端缓存、模型提示词缓存、会话续接当作同一件事，也不承诺固定节省百分比。

## 8. 后续实施与验收顺序

1. 修复协作上下文去重、切换好友/房间身份冻结、成员模型映射；维持现有界面风格。用已有合成基准比较输入量，增加真实切换隔离验证。

3. 增加只读运行能力查询；给文件/API/学习结果添加分段读取与产物引用，复用现有注册表和检索服务。

5. 用同一批任务、同一允许模型、同等思考强度和权限做前后对比：实际输入/缓存/输出 Token、调用次数、工具命中率、验收成功率、失败重试、端到端耗时、宿主 CPU/内存及工具模型 GPU 资源。供应商不报告字段时标“缺失”，不补成真实值。

## 9. 官方依据和开源参考

- [MCP 工具规范](https://modelcontextprotocol.io/specification/latest/server/tools)：工具描述与参数仍需投递，稳定排序有利缓存，列举工具支持分页；实际接入须按客户端协商版本，而不是照最新规范字段盲改旧客户端。
- [Anthropic：通过 MCP 代码执行改善效率](https://www.anthropic.com/research/code-execution-with-mcp)：大型工具清单及中间结果会消耗上下文，按需加载和在宿主处理数据可以减少传递。文中案例节省率不能套用本项目；本轮仅阅读公开文档，没有调用其模型。
- [MCP Python SDK 开源项目](https://github.com/modelcontextprotocol/python-sdk)：实现协议时可优先评估官方 SDK 的协商、输入验证与传输支持；是否替换现有 stdio 服务需对比引入成本和兼容测试，不为了协议名词增加一套服务。

最终建议：**先解决“重复给模型什么”，再解决“通过什么协议给模型”。**
