# 检索、重排、RAG 与记忆的统一优化（2026-10-26）

范围：Open-QQ-Dot 自己的源码（不含 .venv、data 里的技能与模型、dataset_annotation）。所有会检索的模块：QQ 聊天的长期记忆与话题资料、表情与人格模板示例、多智能体协作的经验复用、工具发现、任务查重、失败诊断、任务历史、智能体排错记忆。

## 1. 原来的调用链与瓶颈（读代码 + 实测）

三套检索各自为政：

| 链路 | 用在哪 | 问题（实测见第 4 节） |
| --- | --- | --- |
| `hybrid_search`（BM25 + BGE-M3 + RRF + bge-reranker-v2-m3） | 长期记忆、话题资料、表情、人格模板示例 | 每条回复把最近 3 行聊天各搜一遍、每行重排 30 个候选：42 句消息要 2520 对重排；“好的”“在吗”也照搜；同一事实的两种说法会一起进上下文；记忆与话题两次嵌入同样的几行 |
| `local_retrieval_engine`（FTS5/BM25 + BGE-M3 + 重排） | 经验复用、工具发现、任务查重、失败诊断、任务历史 | 经验/工具/历史永远返回 top-K，没有相关度下限（无关问题也拿到 5 条经验）；查重每个候选单独嵌入一次（16 次/查），且 0.92 的余弦线只找到 9 个改写重复里的 2 个；失败诊断余弦 0.5 让所有无关报错都“匹配”到某个修复；存的向量不记录模型，换模型后会拿不同空间的向量相比；文档按 query 方式嵌入；同一路径以外的调用会替换全局引擎 |
| `agent_memory.retrieve_experience_remedies` | 多智能体规划的“排错经验” | 按空格切词：中文请求是一个整词，几乎匹配不到；英文的 “to” 却匹配一切；排序看重要度而不是相关度 |

另外发现的缺陷：

- 长期记忆写入去重（`memory_management._twins`）和话题去重：已存向量用好友配置的模型，新条目却总用 BGE-M3 嵌入——好友配了自己的向量模型时，在两个不同向量空间之间算余弦（维度不同时还会被 zip 截断）。
- `DynamicContextBuilder` 把所有非踩坑经验都标成 “[VERIFIED] Validated Solution”，包括未验证的候选；第 1 层开头放任务号，任何两次提示都没有可缓存的公共前缀；超预算时从拼好的文本中间截断。
- `persona_vectors` 每次回复都对全部示例跑一遍敏感词正则。

## 2. 新结构

`retrieval_core.py`：一个调度器，所有检索都经过它。

1. **模型登记**：small_models 里已有的 5 个向量模型、4 个重排模型，各自的语言、参数量、显存、质量/速度档；只认磁盘上已有的（不下载、不新增模型）。
2. **选模型**：好友自己的 `retrieval_api` 设置 > 全屋覆盖（`house.local.json` → `retrieval_models: {"embedding": "auto"|名, "rerank": "auto"|"off"|名}`）> 自动：按任务（回复内的 chat/examples/stickers 要快，经验/工具/查重要质量）、语言（只懂英文的模型不用于中文）、文本量（快任务的大批量文本选更快的模型）、GPU 空闲显存（放不下就选能放下的；都放不下选最小的；已加载的不算新占用）。向量模型是“每个集合一个”：查询永远用该集合建库时的模型，所以自动选择只在已装模型变化时才变；云端 API 只在用户自己配置后使用。
3. **缓存**：查询向量与重排分数在内存（LRU，键里含模型签名与产生它的函数，测试替身不会串）；文档向量在磁盘、按模型签名分开存（`DocVectors`，`hybrid_search.cached_vectors` 也改为“每个模型一个向量空间”，旧表自动迁移，保留最近 2 个空间，切回旧模型不必重嵌）。
4. **批量**：多行查询的重排候选合成一批送模型，已打过分的对不再送；文档嵌入一批完成。
5. **结果卫生**：闲聊行不检索（`informative`）；只重排融合后的短名单；相关度下限 + 动态 top-K；近重复去掉后一个（MMR，存量向量余弦 ≥ 阈值或去标点后同文）；任务查重的标识符检查（calc.py 与 utils.py、MySQL 与 PostgreSQL 永不合并）。`rank_texts()` 把整条流水线包成一次调用，给没有自己索引的集合用。

各模块的接法：

- `retrieval_api`：默认路径走调度器选出的模型；BGE-M3 的签名不变（已有缓存继续有效）；查询以查询优先级送本地 worker（原来和文档批处理同优先级）；查询向量走缓存；重排统一走调度器。
- `hybrid_search.gated_recall`（长期记忆、话题）：跳过闲聊行；每行的候选一次批量重排（短名单 12，原 30）；门槛在“三取二”之外加两条窄规则（见 4.3）；结果去近重复。`search()`（表情、模板示例）走调度器并带任务名。
- `local_retrieval_engine`：经验/工具/历史先 BM25 + 向量融合出短名单再重排，按实测下限取舍；存量向量带 `vector_signature`，不一致时批量重嵌并回写；查重 = 余弦短名单 → 重排确认（≥0.97）→ 标识符冲突排除，返回最匹配的一条（原来是第一个过线的）；失败诊断 = 签名精确匹配 → 余弦短名单 → 重排确认（≥0.3）；没有重排模型时用更严的余弦线 0.75；没有向量模型时保留原来的词面规则。每个数据库路径一个引擎。
- `agent_memory`：排错记忆用 `rank_texts`；三种覆盖写（同 key 更新、编辑、纠错）都先把旧版本存进 `memory_history`，`history()` 按同样的属主规则读取。
- `memory_hub.py`（跨智能体记忆）：同时检索 agent_memory 与任务经验，一次排序，每条带种类（偏好、项目事实、任务记录、工具经验、已验证修复、已验证经验、踩坑）和来源（库、id、属主、项目、任务、智能体、是否验证）。可见性：自己的全部；别人的只有“共享且已验证”的（未验证的共享记录可能是给别人智能体下的指令）；项目事实和任务记录不出项目，偏好、工具经验、已验证修复/经验、踩坑可以跨项目；好友私有的 QQ 记忆不在这里。多智能体规划阶段改用它。
- `prompt_context.retrieved_blocks`：一条 QQ 回复里，先把记忆和话题都要搜的几行一次嵌入，再并行检索记忆、话题、模板示例；各线程把检索记录交回调用线程，生成记录不丢条目。
- `DynamicContextBuilder`：第 1 层对所有任务一字不差（可缓存前缀），任务号移到第 2 层；未验证经验标 “[UNVERIFIED]”；超预算先砍代码摘录、再砍最不相关的经验、再砍工具，而不是在中间截断。
- `persona_vectors`：库文件记下建库模型（旧库都是 BGE-M3）；模型不符只用词面；查询向量走缓存；敏感过滤每次加载算一次。

（结果与评分见下文，基准运行结束后填写。）

## 3. 怎么测的（可复现）

- 基准：`tools/retrieval_benchmark.py`，语料 `tools/retrieval_bench_data.py`（全部为合成数据，不含任何真实好友、聊天或任务）：48 条记忆（含近重复、已过期、已被替代）、24 条话题资料（含过期）、34 条任务经验（含另一个属主的私有记录、一条确认失败的踩坑、一对近重复）、36 个工具、16 个任务、10 条失败、8 条排错记忆；每类有带分级标注的查询和负例（闲聊、无关请求）。在临时 `QQ_BRIDGE_HOME` 里建库，只调各模块的公开函数，在模型边界计数（真正送进模型的嵌入文本数、重排对数）。
- 指标：主要条目的 Recall@K、nDCG@K、MRR、返回内容中相关的比例（precision）、负例的噪声率、近重复条数、过期/越权泄漏、P50/P95 时延（热）、首个查询（冷）、进入提示的字符数、GPU 峰值显存。
- 端到端：`--e2e` 用 NVIDIA API 上的 `openai/gpt-oss-20b`（temperature 0，每题 2 次）只依据检索结果完成真实任务：回答好友记忆问题（15 题，含 3 题应答“不知道”）、回答话题问题（10 题，含过期资料与无关问题）、依据团队经验给修复建议（12 题，其中一题检索结果里有“关掉证书校验”的踩坑，回答不得照做）、从工具发现结果里选工具（16 题）。记录成功率与 API 报告的提示 token。
- 对照：改动前的代码取自今天 04:43 的 `Open-QQ-Dot-Development-20261026-Review.zip`（早于本次改动），解压到临时目录，模型目录以只读联接指向同一份模型；与改动后的代码在同一台机器上前后紧接着跑。
- 过拟合检查：阈值是看主查询集的信号后定的，所以另写了一套留出查询（`*_HELDOUT`，定好阈值之后、运行之前写成），新旧代码都跑一遍。
- 降级：`--mode lexical` 关掉本地模型（模拟无 GPU/未装模型）。

**真实与模拟的区分**

| 项目 | 性质 |
| --- | --- |
| BGE-M3、bge-reranker-v2-m3 的检索结果与时延、显存 | 真实模型（RTX 5070，本机另有其他项目占用 GPU，时延有波动） |
| gpt-oss-20b 端到端 | 真实模型（NVIDIA API） |
| 语料与查询 | 合成（为保护隐私，不用真实聊天；真实好友库只有 13 条消息、0 条记忆，无法评测） |
| 其余 3 个向量模型、3 个重排模型的选择逻辑 | 单元测试中模拟“已安装”；本机未安装，未做真实质量与时延测试（按要求不为测试新增模型） |
| 无模型降级 | 真实运行（本地模型开关关闭） |
| 单元测试里的嵌入与重排 | 替身（按关键词给分），只验证逻辑与权限 |

## 5. 结果解读与回退项

**收益**

- 记忆 recall 0.783→0.883，重复项 2→0，重排对数 2520→420，P50 87.7→50.5 ms。
- 经验 precision 0.20→0.93，上下文 6121→1246 字符；工具 precision 0.30→0.66（recall 1.0→0.975）。
- 查重 F1 0.36→1.0，P50 195→33 ms；历史 precision 0.44→1，失败诊断/排错经验的噪声降为 0，排错经验 recall 0.67→1.0。
- GPU 峰值显存基本不变，约 2.2 GB。

**回退与取舍**

- 留出集查重 precision 1→0.78（误合并“购物车”与“D15 支付页”、“微博热搜”与“D14 知乎热榜”），但 F1 0.73→0.875。
- 留出集经验 recall 0.95→0.90，漏掉“npm 代理怎么配”和“rate limit 怎么退避”。
- 历史、失败诊断、排错经验因改为调用模型，延迟约从 15 ms 升至 33 ms；端到端工具选择存在波动。

**事后修复（2026-10-26）**

全量回归 1907 通过、1 失败（`test_round5_integration` 的 `scenario_d`）：无重排器时，查询 `syntax_error_alice_private` 因共享单词 `private` 命中 Bob 的 `database_lock_bob_private`。这是相关性泄漏，不是权限泄漏（SQL 属主过滤仍有效）。已修复 `retrieval_core.strong_overlap`：共享词全部是 snake_case 标识符片段时，要求至少两个片段匹配。受影响测试 59/59 通过；词面基准与 optimized-lexical 完全相同。修复后未重跑全量套件。
