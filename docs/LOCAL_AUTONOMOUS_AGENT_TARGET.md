# 本地自主 Agent 平台：产品目标与验收标准

用户于 2026-10-24 明确的目标：参考 ChatGPT dots、Meta Muse、Grok Bot 的持续工作体验，打造本地运行、支持多账号和多个终端的自主 Agent。此文件是后续审查与开发基准，不表示以下能力均已完成。

## 产品边界

本地常驻服务维护身份、任务、记忆、工具权限与结果；QQ、桌面和网页接入同一服务。关闭界面后，已授权任务继续运行。主机关闭时停止执行，重新开机后从可恢复状态继续。

模型层复用现有 CLI/API/本地模型后端。本地部署指执行与状态在用户控制的设备上；是否要求完全离线推理，仍需用户明确。

## 必须实现的能力

1. 自主执行闭环：目标、计划、执行、独立验证、失败后的有界重试或重规划、结果交付。模型声称成功不能代替验收。
2. 多账号：接入账号分别管理连接、凭据、在线状态和重连；一个账号故障不停止其他账号。多个接入账号必须实际同时在线验收。
3. 多用户隔离：身份、记忆、文件、任务、额度与授权按归属管理；跨账号身份合并和跨项目协作需要显式绑定或授权。
4. 多终端控制：电脑发起、手机查看、网页补充要求或暂停同一个任务；共享稳定任务 ID 和事件记录，不重复创建任务。
5. 多设备执行：如用户要求手机或第二台电脑实际执行操作，则设备需独立注册、认证和上报能力；任务只派往已授权设备。移动网页控制不能作为手机执行能力的验收证据。
6. 持续运行：后台运行不依赖界面；重启后恢复任务、预算、待审批和通知状态；重复事件不重复回复或执行外部操作。
7. 可检查的结果：展示真实执行记录、输出文件、独立验证结果和待人工处理原因；明确区分实测、模拟、未安装与未配置。

## 当前已从代码确认的差距

- `main.py` 的 Bridge 使用全局 `Local\\QQFriendHouseBridge` 锁；`napcat_ws.py` 默认从单份配置建立单条连接。尚不能据此宣称多 QQ 账号并行运行。
- 任务、阶段目标、后台 Worker、独立验证器、Agent 邮箱和按 owner 管理的状态已有基础，应继续复用，避免另起一套任务引擎。
- 桌面和网页已有共同服务接口，但跨终端接续、设备级认证与统一账号管理尚需逐项验收。
- 现有好友工作目录与 Python 权限检查不构成操作系统级隔离；独立账号不得因此获得其他账号的本地凭据。
- 当前已授权的真实 QQ 验收对象仅为用户指定的单个测试好友，具体账号标识不随源码分发；单好友双向收发实测不能覆盖多账号并行和跨设备执行。

## 优先交付顺序

1. 验收当前好友的聊天、记忆、任务、通知和恢复路径，修复端到端断点。
2. 将后台任务运行与界面生命周期解耦，保留现有 EXE 作为控制入口。
3. 在明确“多账号”的具体范围后，实现连接管理与身份归属，并用两个真实接入账号验收。
4. 验收电脑、手机网页间的同任务接续；确认需要哪些设备执行端后再扩展执行节点。

## 核心验收场景

- 发出一个带可检查产物的目标；用户停止发消息、关闭界面后，任务仍能执行、验证并通知。
- 执行中断网或终止后台；恢复后不丢任务、不重复发送已确认消息、不重跑已确认外部操作。
- 两个账号同时接收任务；隔离上下文和数据，停掉一个连接后另一个仍可用。
- 手机与电脑观察同一任务；暂停、补充指令和恢复均作用于同一个任务实例。
- 未授权终端及越权用户被拒绝，且拒绝不会被记成任务成功。

## 待明确的产品选择

- 多账号涵盖多个 QQ 登录账号、多个使用者账号、多个模型账号中的哪些。
- 多终端涵盖访问入口，还是也要求 Android/其他电脑作为实际执行设备。
- 是否要求完全离线模型，还是允许继续使用已配置的云端 CLI/API。
